# Поверхность: приложение (iOS)

Что известно про мобильную дизайн-систему ЦИАН и чем она отличается от вебовой.
Растёт по мере снятия экранов — ниже помечено, что подтверждено, а что ещё нет.

## Источники

> **Компоненты забираем из Figma; витрина — арбитр** (уточнено 2026-08-14 после того,
> как я час выковыривал из скриншотов числа, которые Figma отдаёт готовыми).
>
> - **Figma — рабочий источник.** Геометрия там задана переменными и точна: отступы,
>   gap, радиусы, шкала. Снимать это с картинки дороже и менее надёжно.
> - **Витрина — для того, чего в макете нет:** поведение, жесты, живые состояния,
>   реальный рендер шрифта. И как арбитр: где расходятся — прав код, макет мог отстать.
>
> Правило остаётся парным вебовому «источник истины — кит, а не живой ЛК»
> ([prod-parity.md](prod-parity.md)), но с поправкой на то, что здесь макет машиночитаем,
> а витрина — нет.

| источник | что даёт | как достать |
|---|---|---|
| **TestFlight-сборка кита** на телефоне Романа | **истина**: реальные метрики, поведение, состояния, живой SF Pro | зеркало на мак + `~/.claude/scripts/mirror-shot.sh` |
| Figma «🍏 iOS», `XEzefscTbCTN2RD1t0tVTU` | быстрый способ снять числа, но подлежит сверке | MCP Figma. Часть инструментов требует **выделения** слоя в десктопном приложении |

**Как мерить по витрине.** Зеркало масштабирует картинку, поэтому пиксели со снимка
сами по себе ничего не значат. Калибруемся по известной константе на том же кадре:
высота навбара без крупного заголовка равна 44 pt — из неё получаем масштаб и через
него переводим всё остальное. Пропорции надёжны всегда, абсолютные значения — только
после калибровки.

**Что из этого следует для уже сделанного.** Шкала типографики в
[tokens/surface-app.css](tokens/surface-app.css) снята с Figma, то есть по новому правилу
она **предварительная**. Сверить с витриной, когда дойдём до экрана с текстовыми стилями.

**Про зеркало.** Снимок берётся по id окна, поэтому в кадр попадает только телефон и
работает даже когда окно на другом рабочем столе — переключаться не нужно. Границы
окна ищутся через CoreGraphics: Accessibility окна зеркала не отдаёт вовсе. А вот
**тап через Space не проходит** — чтобы кликать, зеркало должно быть на активном столе.
Отсюда разделение: листает Роман, снимаю я.

## Кит приложения — `kit-app.html`

Страница со всеми компонентами поверхности, рядом с вебовой (`kit.html`). Не путать
с **витриной**: витрина — это TestFlight-сборка кита ЦИАН, арбитр по поведению и
живому рендеру. Кит — наша страница, и она показывает то, что мы уже собрали.

- **Переключатель «Веб / Приложение»** в шапке обеих страниц (2026-08-21). До него
  кит приложения существовал, но на него ниоткуда не было ссылки — то есть найти
  его можно было, только зная имя файла.
- **Две страницы, а не вкладки в одной.** `tokens/surface-app.css` переопределяет
  типографику на `:root`, то есть на весь документ. Уместить обе поверхности в один
  html значит переписать это на атрибут и развести локальные классы обоих китов —
  ради переключателя не стоит. Заодно каждый компонент остаётся в своей среде, а это
  и есть смысл кита.
- **Сам переключатель — не компонент ДС**, хотя Segment Control в ките есть.
  Экспонат не может быть каркасом: сломается компонент — кит должен остаться
  проходимым, иначе поломку нечем будет посмотреть.
- **Показаны и каркасные блоки, не только контролы** (с 2026-08-21): шапка экрана,
  карточка конкурента, нижняя плашка. Шапку добавили потому, что её разметка
  скопирована в пять экранов и сверить копию было не с чем.
- **Чего в ките не будет.** `fixed`-режимы (`--floating`, нижняя плашка в своём
  штатном виде) — накрыли бы саму страницу, поэтому стоят в потоке. Переход между
  экранами — ему нужны две настоящие страницы, смотреть только в прототипе.
- Киты **не уезжают в прод**: `deploy-pages.sh` исключает `kit*.html`. Смотрятся
  локально.

Шесть из одиннадцати имеют вебовый аналог, пять — нет. Это и есть первая половина

На 2026-08-22 не сняты четыре из одиннадцати: Selectable Controls (веб-аналог есть),
Rating Control, Tag Group и Date Picker (аналога нет). Buttons сняты частично —
без Favorite и Info. Тот же список продублирован в ките, секция «Ещё не сделано»:
расходиться им нельзя.

Про №11 стало понятно только на экране отчёта: **Entry Points — это строка-вход в
раздел** (картинка слева, заголовок, шеврон справа), а не какая-то абстракция.
Урок в порядке работы: назначение контрола дешевле узнать по экрану, где он стоит,
чем по оглавлению кита.

Оглавление одной группы ≠ весь кит: в приложении есть и другие разделы, сюда попал
только «Controls».

### 1. Buttons

Снято 2026-08-14.

| подраздел | наш веб-аналог |
|---|---|
| Button | `buttons.css` — `btn-{primary,secondary,outline,ghost}-{lg,md,sm}` |
| LinkButton | аналога нет однозначного. В `links.css` у нас **экшн-ссылки** (`.map-link`, `.add-comment`), а в Figma LinkButton — элемент высотой 44 во всю ширину, текст Heading4 цветом `--text/main/default`. Ближе всего `btn-ghost-*`. Разобраться, что это на самом деле |
| Favorite Button | **нет** |
| Info Button | **нет** (в прототипе отчёта есть похожая `.help-link`, но в дизайн-систему она не вынесена) |
| [Legacy] Button | **не переносим** — устаревшее |

`[Legacy]` подтверждается и в Figma: на странице Button лежат фреймы
«❌ Button | Depricated» и «❌ Link Button | Depricated». Кит в переходном состоянии,
старую кнопку игнорируем.

#### Button — параметры витрины

Снято прогоном по площадке 2026-08-14.

| параметр | значения |
|---|---|
| Enabled | true / false |
| In Progress | false / true |
| Title | текст |
| Subtitle | текст |
| Icon | no icon / local icon / url image |
| Image tint mode | nil / custom tint / original |
| **Style** | primary / secondary |
| **Color** | main / positive / warning / negative / inverted |
| **Size** | small / medium / large |
| Colors Mode | default / light / dark / colored / on overlay(?) |
| Image on Background | false / true |

**Style и Color — две независимые оси.** primary = сплошная заливка + белый текст;
secondary = светлая подложка + цветной текст. Итого 10 сочетаний, все сняты.
`inverted` в обоих стилях выглядит одинаково: белая заливка, почти чёрный текст.

**Расхождение с нашим вебом — в устройстве API, а не в виде.** У нас вариант и цвет
слиты в имя класса, и набор неполный:

```
.btn-{primary,secondary,outline,ghost}-{lg,md,sm}  +  .btn-negative-secondary-{md,sm}
```

То есть `positive` и `warning` как кнопки у нас **не существуют**, хотя токены
`--control-{positive,warning}-primary-*` в палитре есть. А `outline` и `ghost`,
наоборот, есть у нас и отсутствуют в приложении — там их роль закрывает Colors Mode.

Ещё в приложении есть, а у нас нет: `In Progress` (состояние загрузки), `Subtitle`
(вторая строка внутри кнопки), `Colors Mode`, `Image on Background`. Наша кнопка
однострочная и без загрузки.

**Геометрия — из переменных Figma, снятых в режиме iOS.**

| размер | типографика | отступ верт. | отступ гориз. | gap | min-width | min-height | радиус |
|---|---|---|---|---|---|---|---|
| small | **Heading5** 14/17 | 6 | 12 (`unit3`) | 4 (`unit1`) | 36 | 36 | 8 (`--l`) |
| medium | Heading4 16/20 | 12 | 16 (`unit4`) | 8 (`unit2`) | 44 | 44 | 8 |
| large | Heading4 (↯) | 18 (↯) | 20 | 8 | 56 | 56 | 8 |

> ⚠️ **Правилось дважды. Обе неверные версии оставляю здесь, чтобы не наступить
> в третий раз.**
>
> **2026-08-14.** Снял отступы 6 / 10 / 16 с анатомии и решил, что высота выводится
> из них: значит на iOS кнопка ниже — 32 / 40 / 52. Ошибка того же рода, что с
> типографикой: анатомия отрисована **вебовым** режимом переменных.
>
> **2026-08-15, днём.** Нашёл `Button/Subtitle: false/M/VerticalPaddings` = 12 при
> `min-height: 44` и решил, что инвариант — высота, а отступ её добирает, поглощая
> разницу интерлиньяжа. Первая половина верна, вторая — нет.

**Как есть на самом деле.** Проверено двумя узлами, у обоих `FontFamily` = SF Pro,
так что чтение чистое — это режим iOS, а не вебовый:

| узел | размер | типографика | вертикальный отступ | сумма | min-height |
|---|---|---|---|---|---|
| `563:68777` | medium | Heading4 16/20 | 12 | 44 | 44 |
| `64:41643` | small | Heading5 14/17 | 6 | **29** | 36 |

Отсюда три вывода:

1. **Типографика у размеров разная.** Small набран Heading5, medium — Heading4.
   До этого у нас на всех размерах стоял Heading4, и small был на 2px крупнее.
2. **Вертикальный отступ — самостоятельная переменная.** Он не выводится из высоты
   и не обязан её добирать: у small сумма даёт 29, до 36 добивает `min-height`.
3. **Инвариант — `min-height` 36 / 44 / 56.** Он же страхует от вебовых значений
   интерлиньяжа: с ними суммы тоже не сходятся, а высота остаётся.

У large своей переменной пока не встретилось: 18 — по остаточному принципу
(18 + 20 + 18 = 56), и `min-height` его страхует.

Следствие: тач-зону псевдоэлементом добираем **только у small** (36 < 44),
у medium добирать нечего — он ровно 44.

**Ширина.** На площадке два превью: по контенту и во всю ширину. Похоже, что в
приложении это свойство самого компонента, тогда как у нас ширина задаётся снаружи.
Проверить.

> ⚠️ **Цвета со снимка зеркала брать нельзя.** Сверка показала: светлые подложки
> совпадают с нашими токенами почти точно (`#e9effe` против `--solid-blue50` `#e6f0ff`,
> `#edf9e8` против `--solid-green50` `#ebf9e6`), а насыщенные заливки уезжают заметно
> (`#2d6af3` против `--solid-blue500` `#006cfd`). Это характерный сдвиг цветового
> профиля при зеркалировании — он бьёт по насыщенным и почти не трогает светлые.
> Вывод: **витрина — истина для структуры, состояний и поведения, но не для значений
> цвета.** Цвета берём из токенов и Figma.

### Что вылезло при сборке

**В макете смешаны режимы переменных.** Один и тот же Heading5 в соседних слоях
приходит то как SF Pro 14/17/−0.24/590, то как Roboto 14/20/0/500: «4 конкурента» —
в первом виде, «7 конкурентов» и «Продвинуть» — во втором. То же с заголовком
«Мои объявления» (Roboto 28/36 вместо SF Pro 28/34). Это не два стиля, а
непереключённый режим переменных — экран-то приложенческий. В коде везде взята
**роль** (`--type-h5-*`, `--type-h2-*`), поэтому расхождение схлопнулось само.
Хороший довод в пользу правила «значения ролей живут только в токенах».

**Радиус 9px** у блока продвижения в первом и третьем сниппете (во втором — 8).
Девятки в шкале радиусов ЦИАН нет; взяли `--radius-l` (8).

**Асимметричный внутренний отступ.** Блок действий в макете 331 шириной при
контейнере 375 — то есть 20 слева и 24 справа, — а строка статистики под ним 335
(20/20). Взяли 335: 20 с обеих сторон.

**«Рассылка недоступна» не влезает в одну строку.** При реальных ширинах плитке
остаётся 140px под текст, а тексту нужно 150. В макете у строки стоит `nowrap`,
и её просто накрывает иконка «?». В коде оставлен перенос: плитка становится выше,
зато ничего не теряется. Решать: сократить формулировку или принять две строки.

**Живая активность ЦИАН в островке не переносилась** — это декорация макета, а не
элемент экрана; островок отрисован чёрной плашкой, как на живом телефоне. Сам мок
статус-бара прячется, когда экран открыт как веб-приложение с домашнего экрана:
там системный статус-бар уже есть, второй нарисованный был бы дублем.

**Высота навбара 44 не задана, а сходится:** 10 + 24 + 10. Та же константа, по
которой мы калибруем снимки зеркала.

### Шторка действий

Меню по «•••» (node `563:72835`). Открывается у любого объявления — состав один и
тот же, это меню объявления, а не состояния. Условным сделан только **бейдж
«N обновлений»** у строки «Обзор конкурентов»: он и есть флаг из блока конкурентов.
Строка ведёт в отчёт с числом обновлений в ссылке (`report.html?n=5&u=3`).

Бейдж — компонент кита, `components/app/badge.css` (набор Figma `2:7340`, описание
`#Apps`). Две независимые оси, как у кнопки: **ColorType** (main / warning / negative /
positive / ghost / custom) и **Style** (primary — заливка, secondary — светлая
подложка, tertiary — на белом). Цвет задаёт пару `--badge-app-accent` /
`--badge-app-soft`, стиль решает, как её применить, поэтому правил 6 + 3, а не 18.
Высота всегда 24, радиус full, текст Body2, слоты иконок 16 слева и справа,
`--empty` схлопывает пилюлю в круг 24.

**Это не вебовый Label** из `badges.css`, хотя внешне близнецы. У Label цвет —
свободный параметр, у Badge он перечислен осью; по горизонтали у Label 8, у Badge
8 + 2 у текстового контейнера; у Label один слот иконки, у Badge два. Разное API —
не подменяем одно другим.

Заметь: подложка бейджа (`--accent-warning-secondary`, `#ffecd9`) отличается от
подложки жёлтой плитки на экране (`--surface-warning-default`, `#fff2e6`) — это
разные роли, не опечатка макета.

Состояние `Enabled=False` в наборе есть, но по рендеру не отличается от включённого —
что там гаснет, не выяснено, поэтому не переносили.

Отличие от вебового `drawer.css`/`drawer.js` — конструкция, а не оформление: выезжает
снизу, ширины не имеет, закрывается ещё и свайпом вниз, заканчивается home-индикатором.
Общее только затемнение и Esc. Поэтому отдельный компонент, а не вариант шторки.

Ещё два расхождения макета: у всех восьми строк стоит нижний разделитель, включая
последнюю (линия повисает перед home-индикатором — след копирования, у себя убрали),
и строки заданы шириной 333 при контейнере 335 (взяли 335). Скругление шторки сверху
8, а не 16 — так в макете, хотя это ниже системного iOS-шита.

### Возврат из раздела конкурентов — снекбар и пересчёт плитки

Макет `841:91652`, собрано 2026-08-23. Агент выходит из «Обзора конкурентов» — на
«Моих объявлениях» поднимается снекбар «Продолжаем отслеживать N конкурентов —
сообщим, когда будут изменения» (тёмный success, с крестиком). Убрал всех —
нейтральный тёмный «Не отслеживаем конкурентов по этому объекту».

- **Выход — это появление экрана, а не тап по стрелке.** Назад уходят стрелкой
  навбара, системным жестом, кнопкой браузера и «Сохранить и выйти» с настройки.
  Вешать обработчик на каждый путь значит развести одно событие по четырём местам
  и забыть пятое. Поэтому раздел на каждом своём заходе кладёт след в
  `sessionStorage` (`{ from, n }`), а экран «Моих» его читает.
- **Снекбар одноразовый, число в плитке — нет.** След не удаляется, а помечается
  `seen`: всплывающее уведомление переживать перезагрузку не должно, а число в
  плитке обязано. Два разных срока жизни у одного факта — поэтому один ключ с
  флагом, а не два ключа.
- **Плитка пересчитывается вместе со снекбаром — и подпись, и ссылка.** Иначе тост
  спорит с экраном, на котором стоит («отслеживаем 4», плитка «5 конкурентов»), а
  без правки ссылки повторный заход открывает раздел прежним составом, то есть
  убранные конкуренты возвращаются.
- **`from` в ссылке — потому что объект по своим полям не ищется обратно.** Раздел
  знает про объявление `desc`/`price`/`photo`, но найти по ним сниппет в «Моих»
  нельзя, а обновить надо именно его. Отсюда `data-listing` у сниппета и `from` в
  ссылках всех четырёх экранов раздела.
- **🔴 Ноль отслеживаемых подменялся значением по умолчанию — на всех четырёх

  «убрал из отслеживаемых всех, вернулся — они на месте». Вылезло только когда
  снекбару понадобилось **настоящее** число, а не «сколько показать»: до этого ноль

### Snackbar — и что он рассказал про тёмный режим

Компонент библиотеки «🍏 iOS» (`19135:34320`), в наших макетах — `681:20571`:
«Начали отслеживать» после добавления объекта в отслеживаемые (экран `64:39388`).
Файлы: `components/app/snackbar.css` + `snackbar.js`, вызов `showSnackbarApp()`.

Геометрия: 335 × 48, паддинг 12, зазор 8, радиус 8. Иконка 24 прижата к верху
(при двух строках остаётся у первой), текст Body1 16/20 с отступом 2 сверху —
он ставит строку по оптическому центру иконки. Действие — **ссылка** Heading4 с
вертикальным разделителем 0.5 слева, слот один. Крестик — отдельный слот, глиф 16
в коробке 24.

**Чем отличается от вебового Toast** (это разные компоненты, а не один с другими
отступами):

| | веб Toast | приложение Snackbar |
|---|---|---|
| положение | всплывает справа внизу, складывается в стопку | одна плашка во всю ширину за вычетом полей |
| тип | задаёт только глиф, фон всегда тёмный | задаёт **и фон**: neutral / positive / warning / negative |
| действие | до двух кнопок, встают колонкой | один слот, и это ссылка с разделителем |
| текст | Body1 16/24 | Body1 приложения 16/20 |

**Главная находка: тёмный Colors Mode — не отдельная палитра, а те же шкалы с
другого конца.** Разбирая четыре варианта, я снял все восемь значений, и каждое
нашлось примитивом:

| | светлый | тёмный |
|---|---|---|
| фон neutral | `--surface-neutral-default` #f3f5fa | `--solid-gray1100` #212c46 |
| фон positive | `--surface-positive-default` | `--solid-green1100` #103607 |
| фон warning | `--surface-warning-default` | `--solid-orange1100` #472103 |
| фон negative | `--surface-negative-default` | `--solid-red1100` #59030f |
| глиф | ступень 600 (`--icon-*-default`) | ступень 100 |
| ссылка | `--text-main-default` #005ede | `--solid-blue90` #a8cbff |
| разделитель | `--stroke-divider-default` #d0d8e9 | `--solid-gray700` #4f5c79 |

Правило одно на все четыре типа: фон берёт 1100 вместо 50, глиф — 100 вместо 600.
Ни одного подобранного цвета. **Следствие:** завести тёмный режим по-настоящему =
переопределить семантический слой на другие ступени тех же примитивов, а не рисовать
новую палитру. Пока такого слоя нет, режим живёт модификатором `--dark`; появится —
блок в `snackbar.css` схлопнется, и туда же уедут две подстановки из `bottom-bar.css`.

**Глифы держим строками в JS, а не файлами.** У всех четырёх — один путь с одной
заливкой; двухцветными они выглядят за счёт `fill-rule="evenodd"`. Значит цвет
уходит в `currentColor`, и один инлайн закрывает оба режима вместо восьми экспортов.
Тот же приём, что в вебовом `toast.js`.

### Просмотр PDF — шторка во весь экран

Макет `809:74592`, собрано 2026-08-22. «Создать PDF-отчёт» открывает отчёт модалкой
поверх настройки: крестик слева, имя файла по центру, «Отправить» справа.

- **Это третий режим `sheet`, а не новый компонент.** iOS различает `pageSheet` и
  `fullScreen` как две подачи одной модалки — у них общий жест: выезд снизу,
  затемнение, Esc, блокировка скролла. Заводить ради размера второй закрыватель
  значило бы развести поведение по двум файлам. `fullscreen: true` даёт высоту
  `100dvh`, убирает скругление и home-индикатор и добавляет **свой мок статус-бара**:
  модалка накрывает экран целиком вместе с его полкой, и без своей вверху осталась бы
  дыра.
- **`100dvh`, а не `100vh`:** на телефоне адресная строка съедает разницу, и низ
  содержимого уезжает под неё.
- **Отбивка 12 под шапкой — отступом, а не паддингом.** Навбар обязан остаться 44
  (10 + глиф 24 + 10), это его собственная высота; 12 — зазор до содержимого.
- **Крестик тут крупнее:** глиф 16 в коробке 24 против 14 у шторки-диалога. Так в
  макете, и это разные подачи одного контрола.
- **Показываем рендер страницы, а делимся файлом.** PDF в `<iframe>` на айфоне
  открывается не страницей, а встроенным просмотрщиком со своей панелью — окно в окне.
  Поэтому в модалке лежит картинка (`pdf-report-preview.jpg`, страница в семпле одна),
  а «Отправить» отдаёт настоящий `pdf-report.pdf`.
- **«Отправить» — `navigator.share` файлом**, с отступлением по шагам: файл → ссылка
  на страницу → открыть PDF вкладкой. Отказ пользователя (`AbortError`) запасной путь
  **не** запускает: панель закрыли осознанно, а не «не получилось».
- **Вернулся `keepOpen`** — флаг, снятый днём раньше вместе с фильтрами, где он остался
  без пользователей. Здесь у него настоящий случай: панель шаринга поднимается **поверх**
  просмотра, и закрывать из-под неё сам просмотр значило бы отменять то, чем делятся.

### Шапка, которая остаётся на экране — целиком, а не по частям

Решение Романа 2026-08-23, первое применение — «Конкуренты объекта».
`.appbar--sticky` в `components/app/navbar.css`: `position: sticky; top: 0;
z-index: 10`. Шапка **целиком** — стрелка, заголовок, табы, ряд фильтров — стоит в
кадре при прокрутке, лента проезжает под ней. Ни JS, ни модификаторов состояния.

- **Схлопывание попробовали и отменили в тот же день.** Промежуточная версия прятала
  табы и фильтры при прокрутке вниз и возвращала при прокрутке вверх; Роман, посмотрев
  живьём, не принял. Стоила она трёх встречных трансформов, замера двух высот
  `ResizeObserver`'ом на лету, порога против дрожания пальца и покадрового теста.
  **Разница в цене — не аргумент за простое решение, но она показательна:** у sticky
  нет промежуточных состояний, значит нечему разъезжаться.
- **Плата — высота.** На «Подборке» шапка занимает 254 из 852, то есть треть экрана;
  на «Отслеживаются» фильтров нет и она ниже на этот ряд. Ряд фильтров, постоянно
  доступный без прокрутки, стоит этих пикселей — это и было решение.
- **Проверять надо поведением, а не свойством.** `getComputedStyle` вернёт `sticky` и
  там, где прилипание не работает вовсе: его убивает `overflow` у любого предка между
  элементом и скроллпортом. Годная проверка — координата шапки после прокрутки плюс
  `elementFromPoint` по центру контрола: стоит ли он в кадре и доступен ли тапу.
- **Лента под шапкой не должна переверстаться.** Sticky остаётся в потоке, поэтому
  координата карточки в **документе** обязана пережить прокрутку. Это и отличает
  прилипание от любой попытки менять шапке высоту на ходу.

### Прибитая панель кнопок — `sticky`, а не `fixed`

Экран настройки — длинная форма, и кнопки в конце потока Роман попросил поднять на
первый экран (2026-08-18). В макете панель к низу **не прибита**, так что это наше
решение поверх макета.

- **`sticky`** оставляет панель последним блоком потока: контенту не нужен
  дополнительный нижний отступ, а в конце прокрутки она встаёт на своё место.
  С `fixed` пришлось бы вручную резервировать высоту, и она бы висела поверх
  последнего блока навсегда.
- **Инвариант:** отступ панели снизу обязан совпадать с нижним полем экрана.
  Совпадают — панель не дёргается на последних пикселях. У нас оба нуля: панель
  прижата к краю, вырез под home-индикатор добирает её собственный паддинг.
  Зазор 8 по ритму карточек пробовали — под панелью остаётся полоска, в которую
  подглядывает контент.
- **Подложка — матовое стекло** (2026-08-18), то же самое, что у плавающей панели:
  одно правило на оба режима. До этого панель была сплошная белая с тенью
  `0 -2px 12px` и скруглёнными верхними углами — тень отделяла белое от белого.
  Со стеклом граница держится размытием, поэтому тень и углы убраны.
  ⚠️ В конце прокрутки под панелью не карточка, а фон экрана — там стекло читается
  светло-серой полосой, а не белой. Это стекло, а не расхождение.
- Проверять надо поведением, а не классом: видна ли панель без прокрутки, совпадает
  ли её положение вверху и в конце, доскролливается ли последний блок из-под неё.

### Плавающая кнопка — руками собранный `sticky`

На «Обзоре конкурентов» кнопка входа в отчёт лежит во второй карточке, ниже сгиба.
Роман попросил поднять её на первый экран (2026-08-18) — **дублем, а не переездом**:
копия держится у нижнего края, пока настоящая кнопка не доехала до своего места.
В макете этого нет, решение наше.

- **Приземляется, а не прячется.** Пока место кнопки ниже прижатого положения, копия
  стоит внизу; как только место поднялось — копия отдаёт эстафету настоящей кнопке
  ровно в той точке, где та встала. Обе позиции в этот момент совпадают, поэтому
  переключения не видно. Первая версия уезжала вниз и гасла — читалось как «кнопка
  убежала», а не «встала на место».
- **Нативным `position: sticky` этого не сделать.** Sticky не выходит за пределы
  родителя, а родитель кнопки — карточка отчёта, которой на первом экране ещё нет.
  Отсюда `fixed` плюс сравнение двух координат на прокрутке; пересчёт прижат к кадру
  через `requestAnimationFrame`. **Наблюдатель здесь не годится:** он отвечает
  «пересеклись или нет», а нужно знать, кто выше.
- **Внутри — тот же контрол**, что в карточке (`entry-point-app--main`), а не похожая
  кнопка: это одно действие, разойтись им нельзя.
- **Ширину панель держит сама:** `fixed` вырывает её из колонки экрана. Число не
  дублируем — тот же `--screen-app-max`, что у `.screen-app`.
- **Проверять непрерывностью, а не классом.** Тест проходит точку передачи с шагом
  6px и требует, чтобы видимая кнопка не сдвинулась больше, чем прокрутилась
  страница. Скачок сверх прокрутки = кнопка телепортировалась, а не приземлилась.
- **Анимация включается после первого состояния,** отдельным классом. Между
  состоянием и классом — принудительный пересчёт (`void offsetHeight`): без него оба
  изменения попадают в один кадр, и стекло проявляется прямо на загрузке страницы.
  Не `rAF` — тот отдаёт следующему кадру, а зафиксировать надо сейчас. Тот же приём,
  что у сворачивающегося блока в отчёте.
- **Нижнего отступа контенту не даём:** панель гаснет ровно тогда, когда настоящая
  кнопка встаёт на её место, и до конца страницы не доживает.
- **То, что на новых телефонах панели не видно, — это не дефект, а само правило**
  (подтверждено Романом 2026-08-18). Промеряно на проде: при четырёх конкурентах
  кнопка помещается в первый экран на 812 и выше, на Pixel 412×915 панель не
  появляется ни в одной раскладке — там вся страница прокручивается на 28px. Панель
  нужна ровно тогда, когда действия не видно; видно — и она не нужна. Не «чинить».

### Комментарии к конкурентам — экран, шторка-диалог и общий рендер карточки

Экран «Конкуренты в отчёте» (818:82952, 2026-08-18): у каждого выбранного объекта —

### Фильтры — чип открывает шторку, а не красится сам

Раскладка Figma `64:39578`, собрано 2026-08-22. Восемь фильтров, у каждого своя
шторка: чипы (Medium), пара полей «от / до» или слайдер.

- **Чип в ряду — это значение, а не переключатель.** Пусто — показывает ярлык
  («Комнаты»), заполнено — выбранное («Косметический ремонт», «от 25 млн ₽») и
  становится `--selected`. До этого чипы просто подсвечивались по тапу: контрол
  выглядел рабочим, пока его не нажмёшь.
- **Одна таблица держит подпись, тело шторки и отбор.** Разнести их по трём местам
  значит обречь расходиться: формулировка поменяется в чипе и забудется в отборе.
- **«Сбросить» относится к применённому фильтру, а не к черновику.** Пока не нажали
  «Применить», сбрасывать нечего — незаконченный выбор отменяется крестиком. Значит
  действие в шапке решается один раз, при открытии, и по ходу выбора не меняется.
- **Сброс — движение в один тап:** снимает фильтр, обновляет выдачу и закрывает
  шторку. Подтверждать нечего, а показывать шторку с пустым выбором незачем.
  Промежуточная версия («сбросил и выбираешь заново, шторка живёт») потребовала от
  `sheet.js` двух умений — менять действие после открытия (`setBarAction`) и не
  закрываться (`keepOpen`); с окончательным поведением оба остались без единого
  пользователя и **убраны из компонента**. Неиспользуемое API в общей шторке хуже
  его отсутствия: следующий читатель примет его за рабочий сценарий.
- **🔴 Действие в шапке — Heading4, а не Body1** (замечено Романом 2026-08-22:
  «неправильная толщина»). В шкале приложения эти две роли совпадают во всём, кроме
  веса: 16/20/−0.32 у обеих, 400 против 600. Поэтому ошибка не читается ни в размере,
  ни в раскладке — только в начертании, и поймать её может лишь проверка веса.
  Сверено по трём макетам: «Сбросить» (`64:39719`), «Удалить» (`818:83217`),
  «Отправить» (`809:74595`) — все три собраны на `❌ Link Button | Depricated` и все
  Semibold. У `.navbar-app__link`, куда мы переносили тот же контрол на экранах,
  Heading4 стоял с самого начала: разошлись два места одного и того же.
  **Урок шире случая:** там, где роли различаются только весом, «на глаз похоже» не
  работает — сверять надо стиль, а не вид.
- **Действие в шапке прижимает себя само** (`margin-left: auto`). Раньше вправо его
  отодвигал заголовок в шапке с `flex: 1`; в шторке фильтра заголовок стоит строкой
  ниже, распорки не осталось — и «Сбросить» липло к крестику.
- **Chips Medium — 44 и Body1**, не «тот же чип повыше»: у Small кегль Body2. Это
  закрыло дырку, записанную у нас как «в ките только Small».
- **Слайдер собран на нативном `<input type="range">`** — клавиатура, фокус и тач
  достаются бесплатно. Скрипт двигает заполнение и баббл, ручку везёт браузер.
  Дорожка считается по `width − 28`: центр ручки не доходит до краёв на 14 с каждой
  стороны, и без этой поправки баббл на концах разъезжается с ручкой.
- **Радиус по умолчанию 2 км** — как в макете шторки `64:39747` (решение Романа
  2026-08-23; до этого стояло 3 км). ⚠️ В вебовом отчёте тот же чип подписан
  «Радиус 3 км» — там своя раскладка фильтров, не сводили.
- **Радиус включён всегда и не сбрасывается** (решение Романа 2026-08-23,
  подтверждается макетом его шторки `64:39747`: в шапке только крестик, «Сбросить»
  там нет — в отличие от остальных семи). Отсюда флаг `always` у фильтра: чип
  показывает значение с первого кадра, а не ярлык.
- **Радиус в отборе не участвует** — расстояния до объекта в данных нет. Чип
  показывает значение, выдача не меняется; подменять расстояние чем попало значит
  врать в выдаче. ⚠️ В макете слайдер стоит на 2 км, у нас стартовое значение
  3 км — Роман назвал именно его.

#### Предустановка по объекту агента (2026-08-23)

Фильтры приходят на экран не пустыми: они предустановлены по параметрам
оцениваемого объекта — это и есть «подборка», а не «весь Циан».

- **Предустанавливаем три из восьми:** радиус (всегда), комнаты (из описания
  объекта) и площадь ±15% с округлением границ к 4. На данных прототипа это
  33 карточки из 44 — лента остаётся полной, «Показать ещё» работает, конец
  подборки достижим.
- **Цену не предустанавливаем.** Промерено по `competitors-data.js`: комнаты +
  площадь ±20% + цена ±20% оставляют **2 карточки из 44**, ±30% — девять. И по
  смыслу: цена — предмет разговора агента с собственником, спрятать заранее то,
  что дороже или дешевле, значит спрятать сам повод для отчёта.
- **Год и материал — тоже нет:** у 3 объектов из 70 не заполнен год, у 5 —
  материал. Предустановка молча выкинула бы их из выдачи.
- **Объект неизвестен — не сужаем.** Экран открыт без `?desc` — остаётся один
  радиус. Ровно то же правило, что у похожести в вебовом отчёте (`report.js`,
  `distanceToBase`: «объект неизвестен — не сужаем выборку»).
- **Сброс полный: предустановка не возвращается.** Она стартовое предположение, а
  не ограничение, и агент, который её снял, хотел увидеть больше, а не то же самое.
- **Пресет формирует выдачу — и потому связывает флаги.** «Новый конкурент» по
  определению лежит внутри предустановленной подборки (правило Романа 2026-08-23):
  предлагать объект, которого агент в списке не найдёт, — пустое обещание. Отсюда
  общий `preset-app.js`, который знает и о пресете, и о том, проходит ли его
  объект; `updates-app.js` берёт его при выборе кандидатов. Там же теперь
  единственный разбор описания объявления — раньше регулярок было две.
- **🔴 Базовый объект в мобильных «Моих объявлениях» противоречил данным.** Все три
  сниппета были «3-комн. кв., 45 м²» — плейсхолдер из макета, — а все 70
  конкурентов однокомнатные. То есть агент заходил из трёшки и получал подборку из
  одних однушек; предустановка «Комнаты» дала бы честный ноль. Заменено на реальные
  объекты — те самые, чьи фотографии там уже лежали (`mo1`, `mo4`, `mo3` из вебовых
  «Моих»). Вебовая поверхность этой ошибки не знала: там 1-комн. 34–37,5 м², ровно
  медиана данных (35,2).
- **Одна идея, две механики.** В вебе похожесть — *сортировка* (ранжирует, ничего
  не выбрасывая), в приложении предустановка — *отбор*. Допуск ±15% выбран так,
  чтобы она не теряла то, что веб бы показал; если механики решат сводить, сводить
  надо это.
- **Пустой результат объясняет себя** и даёт «Сбросить фильтры». Все конкуренты в
  данных однокомнатные, поэтому выбор «3 комнаты» честно даёт пусто — и это должно
  читаться как ответ, а не как поломка.

### Хвост ленты — компонент `list-tail.css`

Макеты `563:74187` («Показать ещё»), `563:69202` («Это всё, что нашлось») и
`698:76453` («Добавить по ссылке»), собрано 2026-08-22. Всё, что стоит после
последнего объявления — или вместо него.

- **Три вида одного блока, а не три похожих.** Общее: белая карточка во всю ширину
  ленты, радиус 16, содержимое по центру, кнопки во всю ширину. Разное: наполнение
  и поля — 16/20 у «Показать ещё», 20/20/24 у блока конца, 20/20/36 у подвала.
- **Пустое состояние стало компонентом ровно тогда, когда появилось второе
  применение.** До этого «Ничего не нашлось» жило локальными стилями экрана — одно
  место и своего макета нет. Макет конца подборки дал второе, и оба состояния
  оказались одним устройством: иллюстрация 100 → заголовок Heading4 → пары
  «пояснение + кнопка». Разные у них только тексты и набор кнопок.
- **Пар в макете две**, и это не случайность раскладки: «Изменить фильтры» и
  «Добавить из архива» — два разных выхода из одной ситуации. Раз группы заведены
  списком, на архивной вкладке вторая **снимается данными**, а не вторым макетом:
  «Добавить из архива», стоя на архиве, отправляет туда, где уже находишься.

### Переход между экранами — cross-document View Transitions

Push как в UINavigationController: новый экран въезжает справа поверх старого, старый
уходит влево на треть и притемняется; назад — зеркально. Просьба Романа 2026-08-18.

- **Делает браузер, а не мы.** Обе страницы объявляют `@view-transition`, дальше движок
  сам снимает кадр уходящей страницы и анимирует псевдоэлементы. Ни роутера, ни
  перехвата ссылок, ни подгрузки страниц фетчем: навигация остаётся обычной, история и
  «назад» браузера работают сами. Где не поддерживается — переход просто не играет.
- **Направление приходится называть самим.** Для движка «назад» у нас — такая же
  обычная ссылка на предыдущий экран. Уходящая страница кладёт направление в
  `sessionStorage` по тому, на что нажали (стрелка навбара или `data-nav="back"`), новая
  забирает его в `pagereveal` и вешает `data-nav` на `<html>`. Кнопка «назад» браузера
  сюда не попадает — её видно по `navigation.activation.navigationType === 'traverse'`,
  и там назад это или вперёд, говорит **номер записи истории**, а не сам факт traverse.
- **Скрипт направления — в `<head>` и без `defer`.** `pagereveal` приходит раньше конца
  парсинга: с `defer` слушатель не встанет никогда.
- **`prefers-reduced-motion` выключает не анимацию, а сам переход** (`navigation: none`).
  Экран во всю ширину, уезжающий вбок, — ровно то, ради чего эту настройку включают.
- **⚠️ Под автоматизацией переход вешает браузер.** В сборке Chromium из Playwright
  (и headless, и с окном) пришедшая страница не отрисовывается вовсе: ни `pagereveal`,
  ни единого кадра, скриншот и клик висят до таймаута. В обычном Chrome тот же код
  работает — проверено по CDP: пуш, возврат, кадры с параллаксом и тенью. Поэтому весь
  смоук-прогон идёт с `reducedMotion: 'reduce'` (обёртка в `tests/config.js`), а тестам,
  которым нужна анимация (радар, спиннер, сворачивание сводки), заводится отдельная
  страница с движением. **Вывод на будущее: зелёный прогон здесь не доказывает, что
  переход играет, — это проверяется живым Chrome.**

### Матовое стекло — отдельный слой, а не заливка панели

Подложка плавающей панели — `backdrop-filter: blur(12px) saturate(180%)` плюс
прозрачный белый 60% поверх. Насыщенность поднята, как в системном материале iOS:
без неё всё за стеклом выцветает.

**Тени и скруглений у панели нет** (решение Романа 2026-08-18): это не карточка, а
полоса стекла во всю ширину экрана. Значит контент отделяет **одно только
размытие** — и разрежать его дальше нельзя: под стеклом начинает читаться текст, и
панель перестаёт быть границей. Пробовали плотнее (blur 20 и белый 75%) — читалось
как матовый пластик, а не стекло.

- **Живёт в `::before`, а не в `background` панели.** При приземлении гаснуть должно
  ТОЛЬКО стекло: кнопка-копия обязана исчезнуть в тот же кадр, когда её накрывает
  настоящая. Плавно гасить копию нельзя — на экране останется её призрак, пока
  настоящая уезжает вверх. Один слой на двоих такого разделения не даёт.
- **Кнопке нужен `position: relative`.** Абсолютный `::before` иначе накрывает её
  сверху: у потока приоритет ниже, чем у позиционированных потомков.
- **`@supports not` обязателен.** Движок без `backdrop-filter` покажет не стекло, а
  мутную полупрозрачную полосу, сквозь которую читается текст. Там — сплошная белая
  подложка.
- **⚠️ Токена под «материал» в ДС нет** — ни заливки, ни радиуса блюра. Заливку берём
  из палитры (`--transparent-white300a`, 60%), число блюра наше. Дырка в системе.

### `[hidden]` обязан прятать — правило живёт в base.css

Три раза за неделю одно и то же: элемент помечен `hidden`, а на экране висит. Причина
всегда одна — UA-стиль даёт `[hidden]` всего лишь `display: none`, и **любое** авторское
`display` в компоненте его перебивает, молча. Поймались `.price-fields-app` (оба режима
ввода цены разом), `.price-summary-app` (сводка не сворачивалась по ссылке) и
`.market-range-app` (полоса не пряталась выключателем).

Поэтому в `base.css`, в самом резете, стоит `[hidden] { display: none !important }` —
один раз на обе поверхности. `!important` тут не вкусовщина: без него правило снова
проиграет компоненту. До 2026-08-17 та же строка лежала в `<style>` одной страницы, и
соседние экраны оставались с дырой.

**И проверять это надо рендером.** Все три раза тест был зелёный, потому что смотрел на
свойство `.hidden` — оно `true` независимо от того, видно элемент или нет. Годная проверка:
вычисленный `display` плюс нулевой бокс. `offsetParent` для `position: fixed` не работает
вовсе — он там всегда `null`.

### Раскрывающийся блок: `hidden` не подходит, высоту считает JS

Если блок обязан **выезжать**, а не появляться рывком, атрибут `hidden` для него не
годится: `display: none` не анимируется, а правило выше именно его и ставит. Рабочая
схема (сводка цен на экране настройки):

- состояние держит класс-модификатор (`height: 0; opacity: 0`) плюс `inert` — он
  вынимает блок из а11y-дерева и из обхода табом, то есть делает то, за чем раньше
  следил `hidden`;
- **высоту в пикселях ставит JS перед переходом:** у `height` нет интерполяции к `auto`,
  а зашить число нельзя — на узком экране содержимое может стать в две строки. После
  раскрытия высота отпускается обратно в `auto`;
- пересчёт между «зафиксировали высоту» и «поехали к нулю» форсируется **чтением
  `offsetHeight`**, а не `requestAnimationFrame`: отложенный кадр при двойном клике
  добавляет класс уже после того, как блок снова раскрыли;
- `prefers-reduced-motion` гасит переход, и тогда `transitionend` не приходит вовсе —
  JS проверяет `transition-duration` и отпускает высоту сразу.

Проверять такое надо **по кадрам**: во время перехода высота обязана принимать
промежуточные значения. Ассерт «в конце ноль» одинаково зелен и для выезда, и для
мгновенного исчезновения.

### Иконка должна взять цвет текста — значит она инлайн, а не `<img>`

В экспортах из Figma цвет запечён, и `<img>` через `currentColor` не красится — это
записано выше как осознанный размен. Но там, где глиф обязан следовать цвету текста
(шеврон у ссылки `btn-app-link`), размен не работает: экспорт даёт `#212C46` при синем
тексте. Тогда глиф ставится **инлайновым `<svg>` с `fill="currentColor"`** — если у него
один путь и одна заливка, этого достаточно, и второй файл в ките не появляется. Тот же
приём, что у глифов снекбара (`snackbar.js`), только в статической разметке.

### Мок статус-бара — только там, где нет настоящего

Условие в `components/app/navbar.css`:

```css
@media (display-mode: standalone), (hover: none) and (pointer: coarse) { … }
```

Сначала там стоял только `display-mode: standalone` — то есть мок прятался лишь
при «На экран „Домой"». Но с телефона прототип чаще открывают просто по ссылке, и в
Safari получались **две полки подряд**: системная и наша, с разным временем. Нашлось
на живом проде, глазами, а не тестом — тесты гоняли десктопный контекст, где всё
верно. Правильное условие — не «как открыли», а «есть ли у устройства свой статус-бар».

На десктопе мок остаётся: там он и нужен, чтобы экран читался как экран телефона.

### Сафари сама делает из цен телефонные ссылки

Найдено Романом 2026-08-23 на живом проде, на айфоне. Цены в «Моих объявлениях»
(«23 700 000 ₽») и границы оценки на настройке отчёта («14 900 000 ₽ /
17 500 000 ₽») были синими и подчёркнутыми — выглядели кликабельными и вели в
звонилку.

- **Это не наша разметка.** В ней это обычные `<p>`; ссылку рисует детектор
  данных iOS, который сам находит длинные группы цифр и оборачивает их в `tel:`.
  Никакой CSS его не отменяет — тег `<a>` он создаёт уже после парсинга.
- **Лечится одним мета-тегом в `<head>`,** и он нужен на каждом экране:
  `<meta name="format-detection" content="telephone=no, date=no, address=no, email=no">`.
  В `<body>` не действует.
- ⚠️ **В Chromium дефект не воспроизводится вовсе** — детектор есть только у
  Сафари. То есть прогон тестов его не поймает никогда, и ни один скриншот с
  ноутбука тоже. Проверка поэтому статическая: тег есть на всех экранах, и
  список экранов сверяется с содержимым папки — иначе новый экран заведут без
  тега, а тест продолжит зеленеть.
- **Класс находок, а не разовый случай:** платформа дорисовывает то, чего в
  разметке нет, и увидеть это можно только на самом устройстве. Отсюда правило —
  показывать прототип на телефоне, а не только в отладчике с узким вьюпортом.

### Диапазон ширин 360 … 412

`components/app/screen.css`, переменная `--screen-app-max`. Внутри диапазона экран
занимает всю ширину окна, выше 412 — центрируется.

До этого `max-width: 420px` был скопирован в шести местах: три страницы, шторка,
снекбар и нижняя плашка (там как `404 = 420 − 16`). Шесть чисел, обязанных совпадать, —
это не настройка, а ошибка в засаде. Теперь одна переменная, и тест это проверяет
не по коду, а по факту: подменяет `--screen-app-max` на лету и смотрит, поехали ли
следом экран и плашка.

Что замерено на краях (`tests/smoke-app-range.js`, 42 проверки):

- на 360, 375, 393 и 412 все три экрана занимают ровно ширину окна, горизонтального
  переполнения нет нигде;
- на 430 упираются в 412 и центрируются. По краям остаются полоски фона по 9px:
  шапка и карточки упираются в 412, тело остаётся серым. Поднять `--screen-app-max` —
  одно число, если решим, что так лучше;
- ряд табов и ряд фильтров на 360 выходят за край **по замыслу** — они прокручиваются,
  и тест их исключает вместе с содержимым.

**Где тонко.** На 360 у строки цены остаётся 10.5px запаса: суммы в 9 знаков её
переполняют, в 10 — выдавливают документ на 7px. В наших данных максимум ~30 млн,
так что сейчас не проявляется. Подпорку не ставим — увидим на реальных числах,
тогда и решим, как это должно выглядеть.

## Что уже видно по одному экрану

Не проверено замерами, только структурно — зеркало масштабирует картинку, поэтому
абсолютные пиксели со снимка недостоверны, надёжны пропорции.

- **Список — инсет-карточка, а не полноширинные строки.** Белая карточка со скруглением,
  отступ от краёв экрана, лежит на сером фоне. Разделители внутри карточки с отступами
  слева и справа, до края не доходят. Наш будущий компонент ячеек должен строиться так,
  а не «строки на белом».
- **Навбар:** синяя стрелка «назад» слева, заголовок по центру Semibold, стандартная
  высота 44.
- **Текст строки** — Regular, по кеглю похоже на Body1.

## Порядок работы

Идём последовательно: снимаем раздел → сверяем с вебовым аналогом → фиксируем разницу
здесь → и только потом трогаем код. Сначала те шесть, у которых аналог есть: по ним
видно, расходятся ли метрики, или всё сводится к типографике.
